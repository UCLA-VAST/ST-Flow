## What this artifact is

ST-Flow is not a self-contained piece of software. It is a full-stack compiler that
takes a PyTorch model and emits an FPGA bitstream, so the paper's numbers come from
four different layers: an analytical DSE solver, HLS C-simulation, Vitis/Vivado
synthesis and place-and-route, and physical execution on an Alveo U55C. Reproducing
all 206 experiments from source would take **days to weeks** of Vivado time on
licensed tooling and needs a physical Alveo U55C FPGA card.

The artifact is therefore organized in **four tiers**, from "no special tooling" to
"needs our exact hardware". Each tier is independently useful and each states what it
proves.

| Tier | What you run | Needs | Time | Proves |
|---|---|---|---|---|
| **1** | Build the compiler, run the test suite | Linux + Python 3.12 (+ Vitis HLS for csim) | ~15-30 min | the compiler builds and produces correct designs |
| **2** | Regenerate every paper figure and table from archived results | Python only | **~11 s** | every number in the paper traces to a saved experiment |
| **3** | Re-run individual designs end to end | Vitis HLS 2024.2 | minutes to hours per design | Vitis HLS synthesis and cosim (RTL) results |
| **4** | Bitstream + on-board execution | Vivado 2024.2 + Alveo U55C | hours to days per design | the physical results |

All 206 experiments were archived with their generated sources, solver traces, HLS/Vivado reports and on-board logs (`PACT26_Artifacts/`, 5.6 GB, 41,874 files). One command replays the entire analysis pipeline from those archives and reproduces the paper's figures and tables **byte-for-byte**. See [Reproduction fidelity](#reproduction-fidelity).

### Tier 1 claims — the compiler is correct

66 tests (polybench, DNN, synthetic, transformer front-ends) each compile a PyTorch model
and validate the generated design against a PyTorch reference via HLS C-simulation. All 66
pass.

### Tier 3 claims — designs regenerate from source

Re-running a design's DSE → HLS synthesis → RTL co-simulation on the same tool versions
reproduces its archived `main.csv` numbers.

What varies run to run, as a property of the flow rather than a defect:

- **SA/GA-driven designs** (the GPT-2 study, C5) are stochastic by construction — 20
  independent runs per method — so a re-run lands on a different, comparably good point.
- **Vitis HLS/Vivado are not bit-reproducible across tool patch levels.** On a different
  patch level than 2024.2, cycle counts, resource totals and achieved frequency can move.

### Tier 4 claims — the physical results

Generates the physical results behind C6 and the on-board/bitstream columns of C7: needs
Vivado 2024.2, XRT and a physical Alveo U55C. Hours to days per design,
fully supported, not expected within a review cycle. A reviewer without the card loses no
claim: the complete implementation reports and on-board logs for all 206 experiments are
archived, and Tier 2 reproduces the numbers derived from them exactly.

**CODO baseline (C4).** [CODO](https://github.com/sjtu-zhao-lab/codo-artifact) is a
third-party compiler we compared against. We built its open-source artifact separately and
only changed top-level pragmas to use AXI-DMA interfaces, so it shares ST-Flow's off-chip
execution model. The generated designs and full Vitis reports are archived
(`PACT26_Artifacts/codo/`); see [Re-deriving the CODO baseline](#re-deriving-the-codo-baseline)
for how `codo.csv` is re-derived from them.

### Not supported by this artifact

- **Bit-exactness of the synthesized binary** (RTL netlist/bitstream) across Vitis/Vivado
  patch levels, or of a re-derived SA/GA design point. What's verified and exact instead is
  the *reported metrics* (latency, RTL cycles, resource counts) for MINLP designs on the
  same tool versions — the paper makes no binary-level reproducibility claim.

- **Absolute runtimes** (e.g. "MINLP converges in 20–30 s") are machine-dependent, measured
  on our cluster, and will differ on other hardware.

## Getting Started Guide

Target: ~30 minutes, ending with the paper's figures regenerated from archived data.

### Requirements

- Linux x86_64, **Python 3.12** (the pinned wheels are `cp312`-only)
- ~10 GB disk for the artifact archive, ~5 GB more if you build the compiler
- No FPGA, no Vitis, no solver and no network access are needed for the Getting Started path

### 1. Set up (~5 min)

Download the artifact from the archived record (https://doi.org/10.5281/zenodo.21881993) and unpack it. The record
is self-contained: the compiler source, all archived experiments, the prebuilt LLVM/MLIR
toolchain and the pinned Python wheels are all there, so nothing is fetched from the
network during evaluation.

```bash
tar xzf st-flow-pact26.tar.gz && cd st-flow-pact26

python3.12 -m venv .venv && . .venv/bin/activate    # or: pyenv virtualenv 3.12.2 stflow
pip install -r requirements.txt
```

**Starting from a git checkout instead.** The GitHub repository
(<https://github.com/UCLA-VAST/ST-Flow>, tag `PACT26`) holds the same source but not the
5.6 GB `PACT26_Artifacts/` directory. Fetch that directory from the record into the
repository root, then continue as above:

```bash
git clone --branch PACT26 https://github.com/UCLA-VAST/ST-Flow.git && cd ST-Flow
curl -LO https://zenodo.org/records/21881993/files/st-flow-pact26.tar.gz
echo "6efd98fc588cd9fa5c878aa35a872b31  st-flow-pact26.tar.gz" | md5sum -c
tar xzf st-flow-pact26.tar.gz --strip-components=1 st-flow-pact26/PACT26_Artifacts
```

`requirements.txt` alone is enough for Tier 2. The ML front-end and the compiler build are
only needed from Tier 1 onward.

### 2. Reproduce the paper's figures and tables (~11 seconds)

```bash
source env.sh
bash scripts/ae_verify.sh
```

This regenerates every figure and table from the archived experiment outputs into
`ae_verify_out/` at the repository root and diffs the result against the reference copy
shipped in `PACT26_Artifacts/data/`. Nothing in the artifact is modified, and the
regenerated copies are left in place for inspection. Expected output:

```
=== CSVs and LaTeX tables (expect byte-identical) ===
  main.csv                                   identical
  gpt2.csv                                   identical
  codo.csv                                   identical
  gpt2_dse_traces.csv                        identical
  tables/summary_table_bitstream.tex         identical
  tables/gpt2_dse_stats.tex                  identical
  tables/onboard_results.tex                 identical
  tables/robustness.tex                      identical

=== Figures (expect content identical; PDF timestamp may differ) ===
  codo_full_comparison_normalized.pdf        content identical (timestamp only)
  gpt2_convergence.pdf                       content identical (timestamp only)
  ndiv_01_dnn_02_synthetic_speedup.pdf       content identical (timestamp only)
  validation_rtl_cycles_01_dnn.pdf           content identical (timestamp only)
  validation_rtl_cycles_02_synthetic.pdf     content identical (timestamp only)
  validation_rtl_cycles_vertical.pdf         content identical (timestamp only)
  validation_rtl_cycles_wide.pdf             content identical (timestamp only)

15 output(s) reproduced, 0 mismatch(es).
RESULT: PASS
```

`RESULT: PASS` means the analysis pipeline reproduced every paper artifact from the
archived experiments. That is the artifact's central claim.

### 3. Read the numbers back out (~1 min)

The validation statistics behind C1 are printed during regeneration:

```bash
source env.sh
OUT_PATH=/tmp/stflow-ae bash PACT26_Artifacts/experiments.sh 2>&1 | grep -A3 "Accuracy Summary"
```

Expected — these are the numbers quoted in §5.2:

```
  Accuracy Summary for 01_dnn:
    - ST-Flow:   MAPE =   8.24%, Corr = 0.9999
    - Vitis Min: MAPE =  31.41%, Corr = 0.7022
    - Vitis Max: MAPE = 158.05%, Corr = 0.9738
  Accuracy Summary for 02_synthetic:
    - ST-Flow:   MAPE =  17.82%, Corr = 0.9967
```

### 4. Optional: build the compiler (~15-30 min)

Only needed for Tiers 1, 3 and 4. Full instructions, prerequisites and troubleshooting
are in [README.md](README.md#building-and-running). The short version:

```bash
mkdir -p ~/opt && tar xzf llvm-stflow-ubuntu-latest.tar.gz -C ~/opt   # from the record
bash scripts/install_ml_wheels.sh wheels/     # wheels/ at the repository root; needed for Tier 1 and Tier 3 too
source env.sh
export NUM_THREADS=6          # adjust parallelism for the build
python -m pip install -v -e .
python -c "from stflow._mlir._mlir_libs import _streamhls; import stflow.main; print('ok')"
```

If the prebuilt LLVM/MLIR tarball doesn't run on your machine (e.g. a glibc or OS mismatch),
build LLVM/MLIR yourself from `extern/llvm-project` instead: it's the pinned submodule at the
matching commit, so the same CMake/Ninja flow works, but expect **hours**, not ~15-30 minutes —
see [README.md](README.md#step-1--llvmmlir) for the full procedure.

## Step-by-Step Instructions

### Tier 1 — the compiler is functional

Requires the build from step 4 above, plus **Vitis HLS 2024.2** for C-simulation and
**AMPL** for the MINLP solver (both discovered by `source local_env.sh`).

```bash
source env.sh && source local_env.sh
pytest test/                                  # 66 tests
pytest test/ -n11                             # explicit worker count
```

Each test compiles a PyTorch model to an HLS design and runs C-simulation against a
PyTorch reference. The whole suite is **66 tests, all passing**. Measured on a 20-core x86_64 workstation with 23 GB RAM:
**3m42s at `-n11`** and 6m52s at `-n4`, so the `-n10` default in `pytest.ini` is a reasonable
starting point. On a machine with fewer cores than workers, lower `-n` to roughly the core
count: parallel C-simulation is load-sensitive, and oversubscribing makes it both slower and
more prone to spurious failures. Per directory, measured at `-n4`:

| Directory | Tests | Time |
|---|---|---|
| `test/03_polybench` | 21 | ~1.5 min |
| `test/01_dnn` + `test/02_synthetic` | 42 | ~3.5 min |
| `test/00_transformer` | 3 | ~3 min |

If a csim test fails, re-run it alone before believing it: parallel csim under xdist is
load-sensitive, and a failure that reproduces serially is the real thing. Lowering the worker
count to roughly the core count is the reliable fix.

### Tier 2 — full analysis reproduction

`scripts/ae_verify.sh` (above) is the checked version. To regenerate in place and
inspect the outputs directly:

```bash
source env.sh
bash PACT26_Artifacts/experiments.sh          # writes into PACT26_Artifacts/data/
```

`experiments.sh` is the same script used to produce the paper's data. Each step is
annotated with the paper figure or table it produces. It reads only archived reports
and logs — no Vitis, no FPGA, no SLURM, no solver.

Mapping from generated filenames to the paper:

| Generated | Paper |
|---|---|
| `data/figures/validation_rtl_cycles_wide.pdf` | Figure 3 (`figures/validation_wide.pdf`) |
| `data/figures/ndiv_01_dnn_02_synthetic_speedup.pdf` | Figure 4 (`figures/speedup.pdf`) |
| `data/tables/summary_table_bitstream.tex` | Table 4 |
| `data/figures/codo_full_comparison_normalized.pdf` | Figure 5 |
| `data/figures/gpt2_convergence.pdf` | Figure 6 |
| `data/tables/gpt2_dse_stats.tex` | Table 5 |
| `data/tables/onboard_results.tex` | Table 6 |
| `data/tables/robustness.tex` | Table 7 (carried inline in the paper's LaTeX) |

#### Re-deriving the CODO baseline

`codo.csv`, the input to Figure 5, is re-derived from the archived CODO designs by
parsing their raw Vitis reports — `csynth.xml` for resources, latency estimates and
achieved clock, the cosim report for RTL cycles:

```bash
python3 scripts/codo/collect_codo_reports.py -i PACT26_Artifacts/codo/designs/ -o /tmp/codo.csv
cmp /tmp/codo.csv PACT26_Artifacts/data/codo.csv && echo "byte-identical"
```

`experiments.sh` runs this automatically. CODO designs that failed synthesis are kept
separately under `PACT26_Artifacts/codo/failed/` and are not collected; §5.5 discusses
them qualitatively.

#### Inspecting an individual archived experiment

Every design directory holds the complete record of one experiment:

```
PACT26_Artifacts/main/01_minlp_div_min_500/01_dnn/500_01_mlp_mixer_minlp_minlp_no_reuse.prj/
├── 01_pre_hldse_modules/   numbered MLIR after each front-end stage
├── 02_dfg/                 DFG snapshots (.mlir/.dot) per transformation
├── 03_top_modules/         generated top-level modules
├── dse/                    solver traces (minlp_perm_1_final.csv, minlp_unroll_1_final.csv)
├── reports/                phoenix.csv (now stflow.csv), vitis_post_dma.csv, bitstream.csv
├── vitis/, vitis_csim/     HLS project and C-simulation outputs
├── loop_permutation.mod    the AMPL models handed to the solver
└── config.yaml             the exact configuration used
```

`reports/phoenix.csv` (now `stflow.csv`) carries ST-Flow's predicted cost, latency, memory and DSPs; the
`vitis_*` and `bitstream` CSVs carry the measured values. The `p_*` columns of
`main.csv` come from the first, everything else from the latter two.

> **Note on the filename.** These reports are named `phoenix.csv` because the project
> was called Phoenix when the experiments were run; it was renamed to ST-Flow
> afterwards. The reporting code reads either name.

### Tier 3 — regenerate a design from source

Requires the compiler build and Vitis HLS 2024.2. Two examples, picked to bracket the
per-design cost: a small synthetic design (minutes end to end) and a medium DNN design
(around an hour end to end). Both run serially (`-n1`, all three mapping strategies
one at a time) so the times below don't depend on host core count:

```bash
source env.sh && source local_env.sh

# Small: 02_synthetic/random_mlp_seq — DSE + csim
pytest test/02_synthetic/test_06_random_mlp_seq.py -n1   # ~1-2 min

# Medium: 01_dnn/mlp_mixer — DSE + csim
pytest test/01_dnn/test_01_mlp_mixer.py -n1              # ~2-3 min
```

Each produces a fresh `.prj` directory next to its test, structured exactly like an
archived one, and validates the design against a PyTorch reference. Compare its
`reports/stflow.csv` against the corresponding archived `reports/phoenix.csv`.

To synthesize and co-simulate, producing the RTL cycle count that feeds `main.csv`'s
`rtl_cycles` column and the Fig. 3 validation claim (C1):

```bash
STFLOW_MODE=cosim pytest test/02_synthetic/test_06_random_mlp_seq.py -n1   # small: ~10 min
STFLOW_MODE=cosim pytest test/01_dnn/test_01_mlp_mixer.py -n1              # medium: ~1-1.5 hours
```

To synthesize without co-simulating:

```bash
STFLOW_MODE=syn pytest test/02_synthetic/test_06_random_mlp_seq.py -n1     # small: ~3 min
STFLOW_MODE=syn pytest test/01_dnn/test_01_mlp_mixer.py -n1                # medium: minutes to tens of minutes
```

The above times are one mapping strategy's cost times three (measured with all three run
in parallel on a 20-core host, then scaled to serial); a single strategy alone
(`pytest test/01_dnn/test_01_mlp_mixer.py::test_mlp_mixer_balanced ...`) is roughly a third
of it. Times scale with host speed.

**Expected output.** Compare each variant's `reports/vitis_post_dma.csv` (`cosim_latency`,
`dsps`) against the archived `main.csv` row for `01_minlp_div_min_500` (columns
`rtl_cycles`, `v_dsps`). Re-running the commands above reproduced these exactly:

| Design | Variant | `main.csv` `rtl_cycles` (archived) | Expected `cosim_latency` | DSPs |
|---|---|---|---|---|
| `01_mlp_mixer` | no_reuse | 271431 | 271431 | 496 |
| `01_mlp_mixer` | balanced | 271431 | 271431 | 496 |
| `01_mlp_mixer` | max_reuse | 204951 | 204951 | 454 |
| `06_random_mlp_seq` | no_reuse | 11091 | 11091 | 500 |
| `06_random_mlp_seq` | balanced | 7059 | 7059 | 420 |
| `06_random_mlp_seq` | max_reuse | 61917 | 61917 | 20 |

See [Tier 3 claims](#tier-3-claims--designs-regenerate-from-source) for why MINLP designs
reproduce exactly, and what varies for other designs.

### Tier 4 — bitstream and on-board execution

Requires Vivado 2024.2 (`v++` on `PATH`), an Alveo U55C and XRT. Fully supported, but hours
per design and days for the full sweep, so it is not expected within a review cycle. Every
`.prj` directory is self-contained for this — a plain `Makefile`, no SLURM and no `evgen`/
`evrun` needed to build and run a single design:

```bash
source env.sh && source local_env.sh
pytest test/01_dnn/test_01_mlp_mixer.py       # Tier 3 step 1 first: emits vitis/src/kernel.cpp

cd test/01_dnn/500_01_mlp_mixer_minlp_minlp_balanced.prj
make bitstream -j4                            # hours to days: v++ synth + Vivado place-and-route
cd -
# -> .../build/module_top.xilinx_u55c_gen3x16_xdma_3_202210_1.xclbin
```

Then execute the bitstream on the card and validate against the PyTorch reference:

```bash
STFLOW_MODE=bitstream pytest test/01_dnn/test_01_mlp_mixer.py::test_mlp_mixer_balanced
```

This finds the `.xclbin` built above, writes its resource/frequency report to
`reports/bitstream.csv`, and runs the design on the U55C over XRT.

For running the full 126-design sweep at once, `scripts/evgen`/`evrun` fan the same
`make bitstream` + `STFLOW_MODE=bitstream pytest` steps out over a SLURM cluster — that is
a convenience for parallelizing many designs, not a requirement for Tier 4 itself.
`evrun submit`/`status`/`cancel` need SLURM; `evrun report` does not. See
`scripts/EVALUATION_GUIDE.md` and `scripts/EVAL_CHEAT_SHEET.md` for that path.

## Reproduction fidelity

What "reproduced" means here, measured rather than asserted — this is the output of
`scripts/ae_verify.sh` on a clean checkout:

- **CSVs** (`main.csv`, `gpt2.csv`, `codo.csv`, `gpt2_dse_traces.csv`) — byte-identical.
  `main.csv` is 171 rows × 30 columns; all 5,130 cells match.
- **LaTeX tables** (four, including the previously hand-typed Table 7) — byte-identical. The paper's copies under `PACT26/tables/` are
  these files plus hand-added `\vspace` directives.
- **Figures** — the PDF *content streams* are byte-identical; the files differ only in
  the embedded `/CreationDate` and the xref offsets that timestamp shifts. Verified by
  locating the first differing byte in each file and confirming it falls at or after
  the metadata block.
- **Printed statistics** — the MAPE/correlation and speedup summaries printed during
  regeneration match the values quoted in §5.2 and §5.3 to all published digits.

Two pins make this exact and are recorded in `requirements.txt`:

- `matplotlib==3.10.5` — the version that produced the paper's figures. Later versions
  shift tick layout and font subsetting, changing the PDFs without changing the data.
- `pybind11>=2.10,<3` — pybind11 3.x cannot compile the MLIR 20 Python bindings.

## Environment used for validation

The Tier 1 and Tier 2 results quoted above were re-validated from a clean clone on:

- Ubuntu x86_64 (WSL2, kernel 6.18), 20 cores / 23 GB RAM; the MLIR build capped at
  `NUM_THREADS=6` because it is memory-bound rather than core-bound
- Python 3.12.2 in a fresh virtualenv
- LLVM/MLIR 20 (prebuilt release, Release + assertions, Python bindings)
- Vitis HLS 2024.2, AMPL with Gecode

The paper's Tier 3/4 numbers were produced on a SLURM cluster with Vitis/Vivado 2024.2
targeting a Xilinx Alveo U55C at 300 MHz.
